# Architecture — local V1

## Ownership

A single Node HTTP process owns a versioned JSON store and exclusive PID lock. `Engine` keeps the existing deterministic queue, cancellation, and terminal states. `LiveService` executes every run. The dashboard is `/`.

One primary provider session owns a ticket, and every run is Auto: the owner edits a writable worktree. The queue runs up to the tasks-at-a-time setting (1–4, default 1, `DISPATCH_CONCURRENCY` before it is set), each live run in its own worktree; Start now launches one queued run past the limit. Active duplicate tickets are rejected per project and normalized ticket identity. A pending intake guard also prevents repeated submissions while a connector reads a ticket.

## Live lifecycle

`queued → preparing → implementing → validating → [reviewing] → publishing → ready`

`repairing` replaces `implementing` on the single repair attempt. Terminal states for new runs: `ready`, `blocked`, `failed`, `cancelled`, `interrupted` (`planned` survives only on older records). Enabled delivery runs after `ready` and never changes the status; repository notes are recorded after `ready`, `blocked` or `failed`.

A recorded question keeps the implementation state while it waits for explicit response; cancellation/shutdown clears its pending resolver. Restart labels unresolved decisions interrupted and never reapplies them.

A failed check or independent review finding can enter `repairing` once and resume the exact session ID. Authentication/setup problems and explicit worker questions end as blocked; a blocked or failed run (or a ready one) can have its checks edited, which updates the repository recipe and continues in a linked follow-up that revalidates with the new recipe; failures, cancellation, and server interruption never produce a later ready handoff. `publishing` means saving a local commit. Remote writes happen only after `ready`, through delivery connectors the repository has explicitly enabled (see Delivery).

Preparation verifies the run provider's installation/login (a disabled provider blocks the run), snapshots the local base SHA, creates a unique Git worktree/branch, and runs explicitly approved setup recipes. A **plain folder** (a saved repository with `git: false`, registered when `inspect` finds no Git repository at or above the path) has no worktree: the run works in the folder itself (`run.workspace = repositoryPath`, `run.branch = null`, `run.shadow = <dataDir>/shadow/<projectId>`). `src/plain-folder.mjs` keeps a bare shadow Git directory per such project (`core.worktree` pointing at the folder, `info/exclude` holding the default ignore list; the folder's own `.gitignore` applies too) and `workspaceGit(run, workspace)` prefixes every workspace git call with `--git-dir`, so `tree()`, `diff --name-only`, patches, `show <rev>:path` and check reuse are the same code; `read-tree --empty` replaces `read-tree HEAD`. The base is the folder's tree id at prepare time (`baseSha`, `baseSource: 'folder'`), `revision` stays a tree id, no branch or ancestry guard runs, and readiness (`publishInPlace`) only re-verifies the tree: `headSha` is null and `handoff.folder` names the folder. Nothing is ever written into the folder by dispatch except what setup recipes and the dev server's `npm ci` write; a folder that has since gained a `.git` or disappeared blocks the run before any turn. Only one conversation may work in a plain folder at a time: `create` refuses a task whose primary or member folder is a workspace of a working run, naming that task. Plain folders can be members of a multi-repository task (`member.shadow`) and take part in agent mode; `LinkedRepositories` snapshots them in place and never commits them. When the base commit has no `package.json`, the first turn that creates one establishes the protected script baseline (event-logged) so a freshly created repository can be scaffolded in one run; from then on script changes block once, including in follow-ups and edited recipes, unless the repository has `allowSensitiveFiles` on, in which case the new scripts become the baseline (event-logged) without blocking. Continuing a run blocked on changed scripts (`run.scriptsChanged`, or `member.scriptsChanged` for a linked repository) accepts the workspace's current scripts as the baseline (`scriptsAccepted`, `baselineScripts`), and edited recipes keep that accepted baseline. The original checkout is never edited. Recipes are copied into the run record; settings changes never alter a queued or running run. A follow-up picks up the saved checks, setup and check scopes of the primary and of each linked repository when they differ from the run's copy (event-logged; setup re-runs if it changed); a linked repository with unaccepted script changes keeps its old copy so the script block still applies. Each run records `timings` in milliseconds for the CLI check, worktree creation, setup, waiting for the check lock, the local commit and delivery; `src/analytics.mjs` exposes them as `phases` (unknown stays `null` for runs recorded before this field existed) and the Usage drawer lists them under Phase timings. Recipe steps carry a `role` (`check` or `setup`); checks naming long-running npm scripts need `confirmedLongRunning: true`. Runs and agent turns have no wall-clock limit; only individual setup/check steps carry `timeoutSeconds`. After each worker turn, `src/check-scope.mjs` compares the changed paths with the project's `checkScopes` (each `{ id, paths, checks }`; a saved `textOnly` rule reads as one scope named `text-only`). Every changed path must match at least one scope; the checks required are the union of the matched scopes' checks, and the rest are recorded as `skipped` against the revision with the matched scopes named. No scopes or any unmatched path runs every check. Overlapping scopes only add checks. Match-all patterns are rejected. A worker turn that leaves the worktree unchanged ends the run `blocked` before any check runs: there is nothing to test or commit, and files written outside the worktree are never checked or committed.

Optional independent review starts a separate read-only session with the run's provider after mandatory checks pass. A strict JSON verdict must explicitly approve the candidate with no findings. Malformed verdicts, failed reviewer turns, mutations, or cancellation cannot produce a handoff. Findings return to the implementation owner using the shared repair allowance; checks and review rerun on the resulting candidate. Review sessions never replace the owner session ID, and their provider usage is included in totals.

New implementation sessions spawn `codex app-server --listen stdio://`, initialize once, start/resume the exact thread, and start a turn. Owner turns use workspace-write with no native approval escalation; the write roots are the worktree plus the home folder, or `danger-full-access` when the operator chose full access (see Decisions). Questions use server-request/response messages. Independent reviews retain the `codex exec --json` adapter, parsing fragmented UTF-8 JSONL events. Resume always uses the stored session ID, never `--last`. Unknown event types are tolerated; malformed output, missing terminal success/session identity, failed turns, timeout, and unexpected process exits fail closed. Only a valid native completed turn can proceed to validation; cancellation/timeout closes the owned app-server process group before the turn promise resolves. Worker text beginning `DISPATCH_BLOCKED:` requests operator input. CLI credentials remain managed by the CLI.

The composer has no repository picker; the model picker defaults to Auto. Repository resolution runs on the server after intake: a ticket that names exactly one saved repository (whole name, folder name or path) goes there with its saved Linked list, and anything else starts in `dispatch home`, a Git repository at `<data>/home` with no checks that the server creates on first use and recreates if it is deleted. In dispatch home the prompt lists the saved repositories and tells the agent to find the folder the ticket means, ask when the clues fit several or none, and add it through `dispatch_repository`, which the operator approves. No model call routes a ticket. dispatch home is never a linked member or a candidate when the agent decides or tracker intake chooses. An explicit `projectIds` list (first primary) or `all` still works through the HTTP API and `dispatch add --repo`. A tracker link whose connector is read by several repositories, or by none while several are saved, returns a structured repository question (HTTP 409) without creating a run; the answer applies to that ticket only.

## Repositories per task

`POST /api/runs` and `POST /api/tasks` take `projectIds`: an array names every repository (first primary, the rest members, at most 8, exactly as listed), `'all'` hands the choice to the agent, and a lone `projectId` keeps that repository's saved `linked` list as before (`src/repository-selection.mjs`). In agent mode the primary is the repository the ticket mentions first, else the first saved one (`agentPrimary` in `src/repository.mjs`), every other saved repository becomes a member (refused with a question when more than 8 are saved), and member setup is deferred: it runs after the turn, only for members the diff changed, right before their checks, so an untouched repository never pays an install; explicitly ticked members are set up before the turn as before. The prompt says which rule applies. `run.repositorySelection = { mode: manual|auto|agent, reason, projectIds }`, members carry `setup: before|deferred`, and member worktrees are named `<runId>-<repository name>` (id suffix on a name collision). Which repositories changed is decided from each worktree's diff, never by the model. Duplicate exclusion treats a ticket as active in every repository its run works in. A saved task stores `projectIds` (or `'all'`, with the agent primary fixed at save time); `dispatch add --repo a,b` and `--repo all` save the same shape. A repository can also join a running task: `dispatch_repository` (`src/repository-tool.mjs`) saves a folder once the operator approves it in the run, using `repositoryInput` (`src/repository-setup.mjs`, the connect form's suggestions plus overrides, shared with `dispatch repo add` through `POST /api/projects/add`), and records it in `run.linkRequests`. The provider sandbox's writable roots are fixed per turn, so the repository joins on the next turn: when the engine releases the run (`LiveService.finished`), a ready or blocked change run with requests not yet linked queues a follow-up whose `linked` adds snapshots for them; `prepare` creates worktrees only for members without a `baseSha`, and duplicate exclusion covers the joining repositories. Run views expose `repositories` (the primary plus every member with a tested commit, each with its base branch) for the Land and pull request dialogs, which offer one target per repository (`targets` and `bases` keyed by project id).

Setup explicitly refreshes a bounded, paginated [`model/list`](https://learn.chatgpt.com/docs/app-server#list-models-modellist) read through a short-lived Codex app-server connection. Discovery never starts a thread or model turn; merely loading Setup or state performs no discovery. The nonsecret catalog persists in the existing store. Explicit choices are validated against the reported models and reasoning levels. Auto uses the reported default, or existing CLI defaults if no catalog is loaded. The selected model/effort/reason are snapshotted in `run.execution`, passed as native thread/turn settings (CLI arguments for independent review), and copied to follow-ups. Refreshing settings cannot alter queued/running work. CLI availability/account failures still fail closed; no adapter fallback occurs. Claude Code contributes models only when enabled, reporting its documented aliases. Choices are validated by provider and model together, and Auto uses the first enabled provider's default.

A worker's explicit blocked question is persisted as `run.question`. It is rendered as text with an answer composer after the worker has stopped, releasing the active slot. Answering uses the existing follow-up lifecycle, session, workspace, duplicate exclusion, and fresh validation requirements. Native questions can also pause an active owner turn through Interactions; these keep the worker slot until answered or cancelled.

## Validation and follow-up

A temporary Git index captures tracked changes and untracked, nonignored files as a candidate tree. Mandatory commands run against it, with a recipe digest and package-script digest. Each check must exit zero without timeout/cancellation, and the tree is compared after every check. Changes to package scripts stop automatic validation until the operator continues the run, or immediately pass when the repository allows sensitive file writes. Agent edits to other repository code, including tests, remain possible: this is trusted local execution, not tamper-proof independent acceptance.

The workspace branch and saved-base ancestry are verified before validation and again before publication (plain folders skip both and verify the tree id only). Before readiness, dispatch stages the candidate, checks that its tree matches evidence, commits with local dispatch identity and hooks disabled, and verifies the final commit and workspace again. Base SHA, head SHA, tree ID, outputs, and provider reports remain inspectable.

Follow-up creates a new linked run using the existing workspace/session. The older run points to its successor and its evidence becomes historical. Only the newest cycle can be continued. External edits are reflected by the diff endpoint's stale flag. Each cycle reruns its checks, except that a check which already passed on the identical tree id with the identical recipe digest (in this run or an earlier run in the same workspace) is recorded as passed again with `reusedFrom` and zero duration instead of running; failed, cancelled and timed-out results are never reused, and an edited recipe changes the digest.

## Delivery

Delivery runs after the `ready` transition through the repository's delivery connector (a connector with `delivery.*` hooks; see [INTEGRATIONS.md](INTEGRATIONS.md#writing-a-connector)). `Delivery` (`src/delivery.mjs`) owns the orchestration and `run.delivery` (`branch, remote, headSha, pushedAt, pr, ci, error, connector`, plus the ticket writeback result); the connector only talks to its platform. It runs automatically when the run's snapshotted project uses the connector and its push action is permitted. Before any hook, dispatch refuses the base branch, a branch outside `[A-Za-z0-9._/-]` and an untested head. Then `delivery.push`, `delivery.findPullRequest` (reuse, so a follow-up never opens a second pull request) or `delivery.openPullRequest`, and `delivery.checks` for the pushed SHA, each only while its action is permitted; a switched-off read or pull-request action is skipped. Hooks receive `changeFacts` (`src/change-summary.mjs`), never ticket text, and may use `describeChange` for the title and Markdown body (work item reference, SQL to run, where to look, checks, how to test, flags). `refreshDelivery` re-reads the pull request and checks for the recorded SHA and never pushes. A failing CI state is displayed only. A hook error is recorded in `run.delivery.error` with its step (`push`, `pr`, `ci`, `review`) and the connector's `kind`, with a single `delivery` event while the run stays `ready`. There is no background polling in the server beyond the open-pull-request watch; the UI refreshes on demand and every 60 s while a delivered run is visible.

Ticket writeback (`TicketActions`, `src/connectors/tickets.mjs`) calls `ticket.comment` once per ready run when the project uses the ticket's connector and its comment action is permitted, reading `ticket.revision` first when the connector has it; a changed revision prefixes the comment rather than blocking it. No other ticket field is written, and the delivery record makes the comment idempotent. A connector's `status()` is probed only when it is turned on in Settings or used by a repository. GitHub's push path is exercised by `node src/connectors/github/smoke.mjs` against a local bare remote with a `gh` shim; no connector has run against a real service.

## Landing

`Landings` (`src/landing.mjs`) turns ready tasks into a `landing` run that the engine queues, cancels and recovers like any other; `LiveService.work` hands it over. It records `run.landing = { target, strategy, items }` and works in a detached worktree under `live-workspaces/<landing id>` started from `refs/heads/<target>`. Each item is applied by `merge --squash` plus a `<ticketId>: <title>` commit, `cherry-pick --empty=drop` of the task's commits, or `merge --no-ff`. A failed apply is reset, and the task gets a follow-up with `mergeIn` set: `prepare` merges the landing head into the task worktree with `--no-commit`, the owner resolves it in its native session, leftover conflict markers return a repair prompt, and `publish` commits the merge after the task's own checks; the landing starts it with `startNow` so the tasks-at-a-time limit cannot deadlock it, and cancels it if the landing is cancelled. The combined revision then gets the project's setup and `validate` (check scopes from the diff against the target). Only a pass moves the target. `finish` sets `task.landed` and calls `removeWorktree(id, { landed: true })`, which deletes the branch even though a squash leaves it unmerged. A stopped task with `worktreeRemovedAt` is Completed in `taskState`, which is how landed tasks leave Ready for review; `reconcileWorktrees` sets it for worktrees deleted outside dispatch, at startup and on `GET /api/workspace`. `landable(run)` is the one rule for what can land (a tested commit on the primary or on any member); the board hides a landing that is ready or cancelled. A plain-folder member is never a lane: its changes are already in place and `committedMember` excludes it. A task whose primary is a plain folder lands only its Git members: the landing has no target (`landing.target = null`), its own workspace is an unused worktree path, `checkOwn` is skipped, and the task is marked landed without `worktreeRemovedAt`; `taskState` treats `landed` as completed. Pull requests follow the same rule (`publishable`, `PullRequests.base` returns null for the primary and `pullRequest` pushes nothing for it).

## Decisions

Saved tasks retain their explicit model choice. `Interactions` owns bounded pending questions and one-shot operator responses. Native permission grants are declined; the operator's agent access setting decides what an owner turn may write. Approved project setup/check recipes run outside the model sandbox, through a FIFO gate; cancelling a queued recipe removes its waiter. Recovered live PIDs block new work.

The only dispatch tool is `dispatch_question`: 1–3 questions with optional choices, answered by the operator. Codex uses its native question requests instead; Claude Code reaches `dispatch_question` over the MCP bridge. `state.accessMode` (`home` by default, or `full`) is set in Settings → General and snapshotted as `run.access` when a run is queued, so a change never alters queued or running work. `home` keeps each CLI's OS sandbox with network off and adds the home folder as a write root (Codex `writableRoots`; Claude `--add-dir` and `sandbox.filesystem.allowWrite`). `full` removes the sandbox (Codex `danger-full-access`; Claude `bypassPermissions`). Review turns stay read-only in both modes. Files outside the worktree are outside the checked revision: checks do not cover them and nothing there is committed.

Provider plan usage is read on demand from Settings → Usage: Codex through a short-lived read-only app-server `account/rateLimits/read` (no thread or turn); Claude Code through `claude -p /usage --no-session-persistence`, a local command that reports zero turns (anything else is refused); if it fails, the last `rate_limit_event` seen in a dispatch run, stored in `state.providerLimits`, is shown instead.

## Recovery and process boundaries

Shutdown cancels active process groups and ends SSE clients. Cancelling a check or turn signals the process group and every descendant found under it in `/proc` at that moment, so helpers that moved into their own group (Playwright's web server) stop too. Restart marks records that were working interrupted and never replays a task automatically; queued records had not started (a run leaves `queued` synchronously when it starts), so they stay queued and the restarted server starts them. A queue hold (`POST /api/queue/hold` with a lease in seconds, `POST /api/queue/release`) stops new starts without touching working runs; `dispatch update` uses it to wait for an idle moment. Worker/check PIDs are persisted; live work refuses to proceed while a recorded previous worker is alive. An explicit follow-up verifies session availability, branch identity, worktree presence, and duplicate exclusion. PID reuse can conservatively block continuation; inspect the process rather than automatically killing a possibly unrelated PID.

Persistence is atomic file replacement, not a transactional distributed store. Status transitions and user actions write immediately; progress, tool and check bookkeeping coalesce into one write per 100 ms (`Store.saveSoon`), flushed on shutdown, so a crash can lose at most that window of non-transition detail. V1 remains single-process. Sessions/worktrees survive but active terminal processes are not adopted. No hosted service, team access, remote workers, or automatic side-effect reconciliation is claimed.

Writes require JSON. Host/Origin checks and loopback binding remain mandatory. Dynamic content is escaped; tracker HTML becomes text. Connectors parse links into their own allowed arguments rather than fetching arbitrary URLs; a connector is code that ships with dispatch or that the operator added, and runs in the server process with the operator's permissions. Every hook call has a 60 s limit and receives only its arguments and a per-repository context. No command is constructed from ticket text. Child processes use argument arrays and live environments use an allowlist; credentials are not passed in prompts or project settings. Local CLI home access is intentional and is not a credential-isolation boundary against malicious repository code.

## Usage and browser evidence

`runInsights` derives queue/execution/check durations and repair counts from recorded lifecycle timestamps. Input plus output forms the total; cached input is a subset. If any provider turn fails to report a usage field, that run's aggregate field remains unknown. Codex reports cumulative thread totals: the app-server adapter subtracts the pre-turn total (first `thread/tokenUsage/updated` total minus its `last`) and records `last`/`total`; `codex exec` turns report `cumulativeUsage`, and resumed turns subtract the session's previous total stored in `run.usageCumulative` (copied into follow-ups; unknown when absent). Claude reports per invocation. `run.usage.basis` describes this. Admin aggregates only live runs and reports incomplete records separately.

A recipe step with `kind: 'browser-smoke'` (`src/browser-smoke.mjs`, built-ins only) is executed by dispatch rather than as a command: it allocates a free port, starts `step.start` or the first `dev`/`preview`/`start`/`serve` package script with `PORT` set (Vite also gets `--port --strictPort --host`), waits for the URL to answer, runs `scripts/browser-smoke.mjs` from the dispatch checkout (so Playwright resolves from dispatch's own dependencies) to load the page, collect page and console errors and a screenshot, decides pass/fail in `src/` (status below 400, no page errors, no console errors other than a missing favicon), stops the process group, removes untracked files the app wrote into the worktree while it ran (databases, logs) so the staleness check still binds evidence to the candidate tree, and adopts the screenshot as check evidence. The step's fixed `command`/`args` keep it inside the recipe digest, so a changed start script still blocks. After configured browser checks (explicit `browser: true`, or browser/playwright/e2e in the recipe), fresh files in `test-results`/`playwright-report` are copied outside the worktree; collection failures do not change validation decisions. Native app-server browser/Playwright MCP notifications also expose returned image content through an observation callback. Only bounded PNG/JPEG payloads are accepted (1 MB/image, 4/call), and the existing 80-artifact/80-MB run limit bounds retained observations. These images carry source agent and no validation revision, so they never establish check success. No continuous agent-browser video, arbitrary URL fetch or browser control is introduced.

After each check, new/modified PNG/JPEG/WebM/ZIP files from `test-results` and `playwright-report` are copied into `.dispatch/live-artifacts/:runId`. Metadata binds them to check, attempt, revision, and SHA-256. Files are bounded to 20 MB each, 80 files / 80 MB per run; oversized/excess files are omitted and counted. Old attempts retain their copied artifacts. Symlinks and unregistered paths are rejected. Generated workspace outputs must be Git-ignored so required validation does not mutate the candidate tree. Collection applies to browser checks. Screenshots and traces can contain repository/application data and remain private local evidence.

## Frontend

React and shadcn/ui primitives with Tailwind CSS; Vite builds static assets under `dist/client`. The Node backend remains dependency-free at runtime. It serves explicitly allowed page routes and hashed assets. User/Admin are views, not authenticated roles.

`/runs/:id` is a viewport-bounded master/stack tiling workspace (`web/lib/tiles.js`, `web/components/run/`). Chat, Diff, Checks and Timeline tiles are toggled, promoted, closed and resized; layout persists in local storage and mobile shows one tile. The Diff tile fetches `/api/runs/:id/diff` when it is open and the run's status/events/checks change, debounced, never on an idle timer. What opens, moves or takes the run area by itself comes from the chosen layout (Default, Vibe, Technical): `web/lib/run-layouts.mjs` maps each event (first change, ready, browsing starts or ends, the agent replies, a question) to tile actions, `web/lib/run-layout-hooks.js` applies them on the run page, and the Settings preview replays the same rules, so the two cannot drift. In Vibe the Diff tile is neither opened nor fetched until asked for. Usage (run insights) opens in a sliding drawer. Tiles scroll internally; the document does not. Dropdowns use a themed Radix Select with paged options, and tooltips use themed Radix content. Native question choices plus Other drafts persist per request until successful response; text-only legacy blocked questions use Other without inferred choices.

`/setup` contains explicit connection/model discovery. Icon actions retain accessible names and keyboard/hover tooltips; run navigation, decisions and primary actions have visible labels.

`/` is the central composer. Saved repository names/paths mentioned unambiguously select a repository unless the user explicitly chooses one. Adding a repository navigates to the project form, whose folder browser and path field inspect existing Git checkouts; unregistered folders require project recipe approval. Path expansion supports `~/` and server-relative paths without shell evaluation. Draft instructions persist through setup. `/runs/:id` provides a conversation-first page with a chronological index of retained messages, tool output, checks and artifacts across the previous-run chain and tiled Chat, Diff and Checks views. Transitions respect reduced-motion preferences; follow-ups link previous and next conversations. `/setup` (General), `/admin/projects` (Repositories) and `/admin` (Usage) share one settings layout reached from the header gear; `/admin/projects/new` or `/:id` provide repository setup. Native links support direct loading/new tabs and browser back/forward; no operational modal is used. SSE updates the current run; the list polls compact summaries every two seconds while visible and refreshes on return/navigation. Earlier full evidence is fetched on opening a conversation. Repository/model pickers sit in the composer; the theme is in Settings. Tasks moves the composer up and renders the grouped task list below it (`src/board-state.mjs`, shared with the UI); `/api/workspace` summaries carry the blocked question, a pending native question and the stop reason so decisions can be answered from the list. `/` focuses the composer. Browser closure does not stop server-owned processes. Theme/project preferences are local. The logo and abstract motif are inline vectors.

## Module boundaries and optional integrations

`ConnectorService` (`src/connectors/service.mjs`) is the only path from dispatch to a connector. `ConnectorRegistry` holds the loaded connectors, validated against `src/connectors/contract.mjs`; `ConnectorPlugins` loads every folder under `src/connectors/<name>/` that has a `package.json` at startup (`builtinFolders`) and then the folders the operator added, through the same `loadConnector`. A folder that fails to load is reported and skipped. Core code names no connector, so any built-in folder can be deleted. For every hook the service checks the action's permission (repository override, then global switch, then reads on and writes off; `src/connectors/settings.mjs`) and passes `ctx = { signal, settings, memory, remember }`, where memory lives on the saved project as `connectorMemory.<id>`. Intake asks each connector's synchronous `ticket.detect`, then reads through `ticket.read` only when the repository uses that connector with reading permitted; otherwise it returns the 409 connector question. Only a single-line `http(s)://` input is treated as a URL. Auto URL intake considers only repositories that read that connector: none refuses, one is used, several ask for a repository before anything is read. Pasted instructions never require a connector. `status()` probes run concurrently and only for connectors in use. Connector agent tools (`tools` on an action) reach the worker through `DispatchToolCalls`: `ConnectorService.agentTools` lists `<id>_<name>` for connectors the repository uses with the action permitted (read actions only on read-only turns), and `callTool` re-checks both and passes `ctx.workspace`. The tool bridge writes the turn's schemas to its private directory (`DISPATCH_TOOL_SCHEMAS`) because the MCP server cannot import connectors.

`ProviderRegistry` maps provider IDs to adapters and persists explicit consent (`providerSettings`; Codex defaults on, Claude Code off). Every adapter implements `capabilities()`, `models()` and `run()` with the same options and result shape (`completed|blocked|failed|cancelled`, session ID, summary, usage); `CodexAdapter` drives the Codex app-server/exec. `ClaudeAdapter` parses Claude Code's stream-json through the shared `runJsonLines` reader. For interactive turns it opens a `tool-bridge` (a per-turn Unix socket in a private temp directory plus a random token) and hands the CLI an MCP stdio server (`mcp-server.mjs`, Node built-ins) exposing `dispatch_question`. Those calls reach the same `Interactions` path as Codex native questions. Adapters own CLI execution; `LiveService` owns evidence policy; `Engine` owns scheduling and recovery. These modules do not depend on React or HTTP, and can back a future CLI. Connector actions that write outside dispatch are off until switched on, and run only after readiness. dispatch itself stays one repository and package; the only runtime loading is connectors from folders. A task may span several target repositories.

`Memory` (`src/memory.mjs`, Node built-ins) owns per-project notes under `<dataDir>/memory/<projectId>/` — `notes.md` with fixed sections (Build and checks, Gotchas, Conventions, Recent tasks; 8 KB/120 lines, pruning Recent tasks, then Gotchas, then Conventions, never Build and checks) and `tasks.jsonl` (200 lines). `LiveService` calls it twice per run: `memoryBlock` on a new run's first worker turn selects Build and checks plus lines whose words overlap the ticket (capped at 2,000 characters), appends them to the prompt as a labelled data block, records `run.memory = { injectedCharacters, sourceLines, notesBytes }` and one `memory` event; `remember` runs after a ready/blocked/failed terminal state and appends a task summary, with learnings parsed only from the worker's `Notes for next time:` section (three bullets, 200 characters each, de-duplicated) on ready runs. Repairs and follow-ups inject nothing. `project.memory` (default true, including projects saved before the field existed) disables both directions. Notes are never committed to the target repository and never executed. Memory is tested with doubles; its effect on repeated real tasks is unmeasured.

Each new run records worker/reviewer turns with role, duration, supplied prompt characters, resumption flag, and usage. Interrupted/incomplete durations remain unknown. This measures harness-supplied instructions, not the CLI's complete context, and does not imply a model speedup.

## Brain, tickets and branches

`Brain` (`src/brain.mjs`) owns an additive `state.brain` array of memory entries `{ id, kind: rule|note|preference|connector, scope: global|project:<id>, enabled, source: operator|agent|observed, mode, pinned, answers[], origin }`. Rules are the source of truth for `project.instructions` (`syncRules` rewrites the list the prompt reads, so nothing downstream changed); legacy instruction lines are imported once. Notes stay in `notes.md` and are projected into the catalog with deterministic ids; disabling one excludes it from the injected slice, deleting one removes the line. Project connectors are projected from `project.connectors`; a global connector entry is a default for new projects. Preferences are native: `promote()` records answers (last 10) and derives `mode` from the trailing streak (`ask` → `suggest` at 2 → `auto` at 4; a different answer or an undo restarts; `pinned` freezes). `lookup` prefers the project entry, then global. Routes: `GET /api/brain`, `POST /api/brain`, `POST /api/brain/:id`, `POST /api/brain/:id/delete`, `POST /api/brain/forget`; the page is `/brain`. `dispatch_memory` reaches `LiveService.memoryTool`, which may only add or forget agent notes.

The connector contract is in [INTEGRATIONS.md](INTEGRATIONS.md#writing-a-connector). When the pasted input's connector is not used by the candidate repository, intake throws a 409 `question.kind = 'connector'`; `POST /api/projects/:id/connectors` enables it (or a global connector entry in the Brain enables it everywhere) and the composer resubmits. A ticket's `remember` values are stored per repository and handed back to `ticket.detect` as `memory`, so a bare id resolves after the first link. After delivery with a pull request, `TicketActions.offerState` reads `ticket.states` (soft failure, remembered per project and type), pushes an offer onto `run.offers[]`, applies it at once in `auto` mode with a revision check, and otherwise leaves it pending for `POST /api/runs/:id/offers/:offerId` (`value`, `skip`, `never`) and `/undo`. Branch names come from `src/branch.mjs`: the `branch.template` preference (tokens `{type} {ticketId} {id} {run} {slug}`) or `dispatch/<run>`, made unique with a numeric suffix; a ticket from a connector gets the id `<CONNECTOR>-<id>`.

## Provider contract, tools and steps

Every adapter exposes a static `contract` (`questions: native|tool|none`, `tools: mcp|none`, `browserTools`, `sessions`, `streaming`, `readOnlyTurns`, `readOnlyTools`); `ProviderRegistry.contract(id)` reads it through `adapter(id)`, so a disabled provider is still never touched. `src/dispatch-tools.mjs` is the registry (`dispatch_question`, `dispatch_memory`, `dispatch_repository`, eleven `dispatch_browser_*` tools) and `toolSet()` the only gate; `DispatchToolCalls` (`src/tool-calls.mjs`) decides the list per turn from the contract and project settings and handles every call the same way whichever CLI carried it. The bridge (`src/tool-bridge.mjs`) advertises only the supplied tools (`DISPATCH_TOOL_NAMES`), returns MCP content unchanged, and renders Codex config overrides (`codexMcpArgs`, `tool_timeout_sec=600`). Claude derives `--allowedTools` from the bridge names; Codex appends the overrides to app-server and exec. Adapter-specific and left so: Codex native questions versus the question tool, Claude's per-tool allow list versus Codex's per-server config, `MCP_TOOL_TIMEOUT` versus `tool_timeout_sec`, and Codex review over `exec` stays toolless.

`StepLog` (`src/steps.mjs`) appends one JSON line per step to `<dataDir>/live-steps/<runId>.jsonl` (32 KB per line, 64 MB per file then one `overflow` step): `turn.start/end`, `message`, `tool.call/result` (correlated by `callId`, full bounded input and output, dispatch tool calls included), `browser.step`, `files`, `check.start/end` (with `artifactIds`), `question`, `answer`, `delivery`, `status` (through `Engine.onTransition`), `dev-server`, `patch`. `run.stepCount` and `run.stepSummary` ride the SSE snapshot; `GET /api/runs/:id/steps?after&limit` pages by sequence. Artifacts carry `stepId`. After each owner turn `savePatch` stores `turn-<attempt>.patch` (2 MB cap) as an artifact, and `diff()` serves the latest patch once the worktree is gone. `run.events` stays the bounded summary; the raw log rotates once at 16 MB. `GET /api/runs/:id/export?format=zip` (`src/zip.mjs`, store-only, built-ins) bundles run, steps, raw logs and artifacts.

## dispatch browser

`project.browser = { enabled, headed }`: off unless set; the connect form pre-ticks it when `inspect` reports a `dev`, `preview`, `start` or `serve` script (`suggestBrowser`), repositories dispatch creates get it on, and saved repositories keep their setting. When on, `DispatchToolCalls` attaches the browser tools and `LiveService.browserFor` lazily spawns `scripts/browser-host.mjs` (Playwright `launchPersistentContext`, profile `<dataDir>/browser-profiles/<projectId>` with a PID lock, headless unless the run or project asks for a window) through `BrowserSession` (`src/browser-session.mjs`, JSON lines over stdio, one call in flight, fails closed on malformed output). The browser is dispatch's child: it has network and sits outside both CLI sandboxes; the CLI only runs the thin MCP client. `src/browser-tool.mjs` validates arguments (http/https/app URLs, `eN` refs, key names, waits ≤ 30 s), resolves `app:/` through `src/dev-server.mjs` (the same start logic as the smoke check, on a free port, stopped before validation and at the end of the run), and records each call as a `browser.step` with url, title, the acted element's box, console errors, duration, error and a post-action JPEG stored by `BrowserEvidence.keepStep` under a separate budget (400 files, 60 MB; over budget keeps the step without pixels). Actions return the accessibility snapshot as text; only `screenshot` returns pixels to the model. Answer-only turns may look but not act.

## Task storage

`Tasks` stores local requests in the version-2 store's additive `tasks` array. Older stores acquire an empty array. Saving performs no intake, workspace creation or provider call. Explicit start calls the existing `LiveService.create`; an internal `taskId` is added before the run's first atomic store save. Concurrent starts coalesce in memory; persisted linkage prevents replay across restarts. Failed intake leaves the task retryable. Lists resolve linked follow-ups to the newest available cycle. HTTP callers cannot attach arbitrary task IDs through direct run creation.

`Board` keeps operator metadata in the store's additive `board` object (`folders`, `items`), keyed by conversation: the saved task id when the conversation started from one, otherwise the root run id. Run records stay untouched evidence. A task's group is derived deterministically from its latest run's status plus that metadata (`taskState`). Pause and done record the run id they were set on and apply only while it is the latest run, so any follow-up clears them. Pausing a running turn uses the same cancel-then-follow-up path as interrupt, split into two operator actions.

`createServer` snapshots the built client assets once. HTTP serves those buffers for the process lifetime even if files are rebuilt/deleted later. Backend imports remain loaded normally; use the non-watching `npm start` process for serving. The server must be intentionally restarted to adopt a new build. This keeps the UI available while its own checkout is rebuilt; it does not protect against OS crashes or same-user process signaling.
